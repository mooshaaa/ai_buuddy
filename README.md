# AI-buddy: AI-наставник для стажёров

Прототип для хакатона Hack&Change 2026 (кейс Авито, автор кейса Changellenge).
AI-buddy помогает стажёру пройти адаптацию: отвечает на вопросы **строго по базе знаний** с указанием источника,
совершает **реальное действие** через корпоративный сервис (заявка на отгул) с сохранением результата,
показывает этапы адаптации из чек-листа и **учитывает права доступа** стажёра и наставника.

Все данные синтетические. Демо-регламенты в базе знаний помечены «демо».

- Видео-демонстрация: [AI-buddy_video.mp4](AI-buddy_video.mp4)

## Быстрый запуск (Docker)

Нужны Docker и Docker Compose v2. Проверено на Docker 28.4.0 и Compose 2.39.4 (WSL 2, Ubuntu).

```bash
git clone https://github.com/mooshaaa/ai_buuddy.git
cd ai_buuddy
docker compose up --build
```

Ключи и файл `.env` **не нужны**: без ключа система работает в режиме заглушки, и все сценарии доступны.
Первая сборка занимает несколько минут.

| Что | Адрес |
|---|---|
| Интерфейс | http://localhost:5173 |
| API и документация | http://localhost:8000/docs |
| Проверка режима модели | http://localhost:8000/health |

Остановить: `Ctrl+C`, затем `docker compose down` (добавьте `-v`, чтобы стереть данные БД).

### Запуск с живой моделью

```bash
cp .env.example .env
```

Откройте `.env` и заполните:

```
LLM_PROVIDER=openai_compat
LLM_BASE_URL=https://api.groq.com/openai/v1
LLM_MODEL=openai/gpt-oss-120b
LLM_FALLBACK_MODEL=openai/gpt-oss-20b
LLM_API_KEY=<ваш ключ>
```

Затем `docker compose up`. Откройте `/health`: при работе модели в поле `llm` будет `openai_compat:openai/gpt-oss-120b`.
Если в поле `stub`, модель не подключена (проверьте `.env`).

## Как проверить за 3 минуты

Тестовые пользователи выбираются в шапке интерфейса (вход без пароля, это прототип):

| Пользователь | Роль | Id |
|---|---|---|
| Анна | стажёр | `intern_1` |
| Игорь | наставник | `mentor_1` |

Сценарии для проверки (от имени Анны, если не указано иное):

1. **Действие через сервис.** «Хочу отгул в понедельник» → карточка с параметрами → «Подтвердить» →
   мок-сервис отсутствий возвращает номер заявки → заявка сохраняется в БД. Понимает также «послезавтра», «20 ноября» и т. п.
2. **Знания с источником.** «Как запросить доступы?» → ответ и блок «Источник» с названием пункта чек-листа.
3. **Честное «не знаю».** Вопрос, которого нет в базе, → бот говорит об этом и советует обратиться к наставнику или куратору.
4. **Права доступа.** От Анны: «Покажи прогресс стажёра» → отказ. От Игоря тот же запрос → данные.
5. **Память диалога.** После «Хочу отгул» уточните «а на 25-е?»; обновите страницу, диалог восстановится.
   Кнопка «Новый диалог» архивирует историю.
6. **Этапы адаптации.** Панель справа: этапы из чек-листа, отметка выполнения, следующий шаг.

## Возможности

- **Чат** с ответом в виде списка типизированных блоков: `text`, `error`, `action_card`, `source`.
- **Действие «отгул»:** запрос → карточка → подтверждение пользователем → вызов мок-сервиса → запись результата в БД.
  Действие не выполняется без явного подтверждения.
- **База знаний** (`backend/app/kb.py`, 17 записей): пункты чек-листа стажёра и демо-регламенты.
  Ответ строится только по записям; выдуманные моделью id источников отбрасываются; без валидного источника ответ считается «не найдено».
  Записи, предназначенные наставнику, скрыты от стажёра.
- **Память диалога:** модель получает последние 8 сообщений (по 1 500 символов) как данные, а не как инструкции.
  История хранится в таблице `messages`.
- **Права доступа:** единая точка проверки роли перед каждым вызовом инструмента.
- **Интерфейс не блокируется** на время вызова модели: запрос обрабатывается отдельно от UI, отображается состояние ожидания.
- **Устойчивость к сбоям модели:** основная модель, запасная модель, затем заглушка на правилах.

## Архитектура

```
Браузер (React + TypeScript + Vite)
        │  POST /api/chat
        ▼
FastAPI ── agent.py: понять запрос → проверить права → вызвать инструмент → собрать блоки
        │        │                          │
        │        ├─ llm/                    ├─ policy.py   права по ролям (единая точка)
        │        │   OpenAI-совместимый API ├─ tools.py    мок корпоративных сервисов
        │        │   → запасная модель      ├─ kb.py       база знаний с источниками
        │        │   → заглушка на правилах └─ history.py  память диалога
        ▼
PostgreSQL (SQLite в тестах и локально)
```

Структура репозитория:

```
backend/app/
  main.py      эндпоинты
  agent.py     оркестратор
  policy.py    права по ролям
  tools.py     мок корпоративных сервисов (create_absence, view_team_progress)
  kb.py        база знаний
  history.py   память диалога
  llm/         интерфейс провайдера, OpenAI-совместимый клиент, заглушка, откат
  models.py    таблицы БД
  seed.py      синтетические данные из чек-листа
  schemas.py   контракт блоков ответа
  debuglog.py  отладочный журнал (только при DEBUG=1)
backend/tests/ тесты (pytest)
frontend/src/  App, Chat, Blocks, StagesPanel
docs/          спецификации (SDD)
```

### Права доступа

| Роль | Разрешённые инструменты |
|---|---|
| Стажёр (`intern`) | `create_absence` |
| Наставник (`mentor`) | `create_absence`, `view_team_progress` |

Проверка выполняется на стороне сервера при каждом вызове инструмента, а не в интерфейсе.
Роль определяется по пользователю в БД, а не по тексту сообщения.

### Подключение корпоративных сервисов

Сейчас сервис отсутствий реализован как мок в `tools.py`. Агент вызывает инструменты через единую функцию `execute`,
поэтому замена на реальный API или MCP-сервер сводится к замене реализации инструмента, а проверка прав и сохранение результата остаются прежними.

## Безопасность работы с моделью

- Модель только **извлекает намерение и параметры**. Инструменты вызывает код агента после проверки прав.
- Действие с побочным эффектом выполняется только после подтверждения пользователем на карточке.
- Текст пользователя и история диалога передаются модели как данные.
- Ответы по базе знаний проходят проверку: источники должны существовать и быть доступны роли пользователя.

## Переменные окружения

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `LLM_PROVIDER` | `stub` (без модели) или `openai_compat` | `stub` |
| `LLM_BASE_URL` | базовый URL OpenAI-совместимого API | пусто |
| `LLM_MODEL` | основная модель | пусто |
| `LLM_FALLBACK_MODEL` | запасная модель | пусто |
| `LLM_API_KEY` | ключ API (не коммитить) | пусто |
| `LLM_TIMEOUT` | таймаут запроса к модели, секунды | `15` |
| `DEBUG` | `1`: отладочная строка под ответами и `/api/debug/events` | `0` |
| `DATABASE_URL` | строка подключения к БД (в Docker задаётся в compose) | `sqlite:///./app.db` |

Модели, использованные при разработке: Groq `openai/gpt-oss-120b` (основная) и `openai/gpt-oss-20b` (запасная).
Для сдачи оставляйте `DEBUG=0`.

## API

| Метод и путь | Назначение |
|---|---|
| `GET /health` | статус и режим модели |

## Метрики пользы

Для оценки эффекта на реальном пилоте предлагаются три метрики, которые считаются по журналу сообщений и действий:

| Метрика | Как считается |
|---|---|
| Доля вопросов, закрытых без наставника | вопросы с ответом из базы знаний / все вопросы |
| Время до первого действия | от первого сообщения стажёра до подтверждённой заявки |
| Число оформленных заявок через бота | записи в таблице действий по периодам |

Проверка эффекта: сравнение групп стажёров с ботом и без него. Подробности: `docs/`.

## Известные ограничения

- Вход без пароля: `user_id` передаётся в запросах, история открывается по идентификатору. В продакшене нужна авторизация.
- Все данные и сервисы синтетические, сервис отсутствий мок.
- На нерелевантные вопросы вне темы адаптации бот может отвечать справочно.
- Заглушка без модели ищет по ключевым словам и точна меньше, чем модель.
- Бесплатный лимит Groq при длинных диалогах возвращает ответ 429, тогда включается заглушка.
- Фронтенд в Docker запущен через dev-сервер Vite (для прототипа). В продакшене нужна статическая сборка.
- Зависимости dev-инструментов фронтенда имеют известные уязвимости (`npm audit`). На прототип с синтетическими данными это не влияет.
